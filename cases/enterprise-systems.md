## 案例一：给既有 Web 审批流程增加节点

**业务需求。** 部分销售、采购流程需要新增审核节点，同时维持其他流程原样。新增审核角色需要更广的查看范围，但只能处理当前轮到自己的单据；拒绝后要退回发起人重新编辑。

**技术环境。** 仓库为 C# / ASP.NET MVC，项目文件目标为 .NET Framework 4.8，配有 Razor 页面、业务管理与数据访问层、SQL Server 脚本及 IIS 发布说明。开发恢复依赖 Visual Studio / NuGet 工具链；这些是既有系统环境，并非我从零选型的成果。

**实现路径。** 需求响应文档将修改拆到角色定义、流程配置、列表过滤、审核入口、前端步骤判断和数据库迁移。关键点是分开“能够看见单据”和“能够审核当前节点”，并检查所有依赖步骤序号的界面行为。

**在途数据与重复部署。** 新节点不仅影响新单据，还影响正在流转的记录。迁移加入执行记录，避免重复执行时把在途步骤再次顺延。这里展示的是对既有状态与上线过程的考虑，不公开内部审批图、角色 ID 或数据库表结构。

**验证与交付状态。** 2026-08-04 需求文档记载已完成代码、部署辅助文件、迁移防重复保护和格式检查；同时明确本机缺少 ASP.NET / IIS / SQL Server 环境，未做真实编译与数据库联调。文档中的流程验收清单是上线前待执行步骤，不能描述成全部实测通过或已经生产上线。

## 案例二：恢复并维护 Flutter 安卓 / iOS 项目

**交接问题。** 过程记录描述移动端源码和数据库备份可用，但历史后端源码不完整，Flutter、插件及平台构建链老旧，单纯打开页面无法确认业务是否正常。

**需求与取舍。** 先固定旧环境作为恢复基线，再推进保守升级。2026-06-29 记录把 Flutter 3.7.12 / Dart 2.19.6 作为当时升级测试主线，避免同时引入 Dart 3、插件 API 和多个平台的全面迁移。这是当时的版本策略，不代表当前推荐版本或所有平台已经完成升级。

| 工作层面 | 记录中的具体实现 | 验证边界 |
| --- | --- | --- |
| Flutter 业务层 | 处理登录缓存、角色跳转、权限缺失引发的空白页，登出清理导航栈 | 不能因页面可用就认定所有业务流通过 |

## 一次可说明的故障定位

2026-06-23 的“手机无数据 / 网络超时”记录分别检查本地测试服务、临时转发地址和后端响应。发现某些响应虽然 HTTP 状态为 200，内容却是 HTML，而客户端期待 JSON。

这个案例体现排障时要看响应内容与运行环境，而不能只看状态码或把问题归因于 Flutter 升级。记录给出恢复接口访问的方案；不把建议步骤自动写成生产修复完成。
